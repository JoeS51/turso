Who owns the query?

Turn your correct request-pipeline model into a code map: which component calls the next one, and what data crosses each boundary?

Your Model, Tightened

Your model is right:

PG bytes → SQL → PG AST → Turso AST → VDBE → Turso rows → PG responses

One correction matters: cli/main.rs does not call do_query. It starts server mode. The pgwire crate later calls do_query when a client sends a simple-query message.

First: The Binary Has Two Paths

tursopg is one binary with two relevant modes. Both open Turso with PostgreSQL behavior, but only one speaks the PostgreSQL wire protocol.

1. The CLI launches a server.

// postgres/cli/main.rs
if let Some(ref address) = opts.server {
    let server = TursoPgServer::new(address.clone(), db_file, conn, interrupt_count);
    return server.run();
}

2. The server gives each socket to pgwire.

// postgres/server/lib.rs
let (socket, addr) = listener.accept().await?;
tokio::spawn(async move {
    process_socket(socket, None, factory_ref).await
});

run_async owns listening and connection acceptance. process_socket belongs to pgwire; it owns PostgreSQL frame decoding and encoding.

3. The factory tells pgwire which Turso callbacks to invoke.

// postgres/server/lib.rs
fn simple_query_handler(&self) -> Arc<impl SimpleQueryHandler> {
    self.handler.clone()
}

TursoPgFactory connects pgwire's protocol machinery to TursoPgHandler. This is callback registration: Turso does not call do_query; pgwire calls it.

What “Prepare” Means Here

At prepare_statement, the SQL has already left the protocol layer. This function coordinates PostgreSQL compatibility:

  1. Handle frontend-only statements such as SET, SHOW, schemas, and file-based COPY.
  2. Ask pg_query for PostgreSQL's parsed protobuf AST.
  3. Ask PostgreSQLTranslator for Turso's AST.
  4. Pass that Turso command and session options into core.

Core then compiles the Turso AST into the VDBE program stored in a Statement. Later, execute_query or execute_non_query runs that statement.

The Return Trip

The phrase “server translates the Turso response” is close, but the exact flow is:

Turso Statement yields Value objects
  → server chooses PostgreSQL field OIDs
  → server encodes values into DataRow objects
  → server returns pgwire Response objects
  → pgwire serializes PostgreSQL response bytes

The server owns semantic mapping, such as deciding that a Turso integer column should be PostgreSQL INT4. pgwire owns the final protocol framing.

Primary source
Compare this implementation with PostgreSQL's specified simple-query response sequence: RowDescription, zero or more DataRow messages, CommandComplete, then ReadyForQuery.

Boundary Check

A Focused Code Tour

Read only these slices, in this order. At each stop, identify the artifact entering and leaving.

  1. postgres/cli/main.rs:1024-1035: choose server or direct CLI mode.
  2. postgres/server/lib.rs:55-100: accept sockets and enter pgwire.
  3. postgres/server/lib.rs:156-205: register and run the simple-query callback.
  4. postgres/frontend/session.rs:169-209: parse, translate, and cross into core.
  5. postgres/parser/translator.rs:114-181: dispatch PostgreSQL AST nodes.
  6. postgres/server/lib.rs:384-418: run and return pgwire responses.

Do not read each whole file yet. The translator alone is thousands of lines; first learn its boundary and dispatch shape.
