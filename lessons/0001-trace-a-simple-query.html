Trace one query

By the end, you can follow SELECT 42 from a PostgreSQL Query message to Turso core and back to PostgreSQL response frames.

The Mental Model

The “PostgreSQL frontend” is not one crate. It is a pipeline around Turso core. The server speaks PostgreSQL to the client; the parser and translator adapt PostgreSQL SQL; core remains the execution engine.

  1. Wirepgwire decodes Q and calls Turso
  2. Sessionsplit and prepare PG-aware SQL
  3. TranslationPostgreSQL AST becomes Turso AST
  4. Executioncore compiles and runs a statement
  5. Encodingrows become PG metadata and frames

Primary source
The PostgreSQL specification defines a simple query as a Query message followed by response messages and a final ReadyForQuery. Read Message Flow: Simple Query.

Follow SELECT 42

1. pgwire hands Turso a string. TursoPgHandler::do_query receives &str. The byte-level Q + length + SQL + NUL parsing is owned by pgwire; Turso's raw test client constructs that exact frame in send_query.

// postgres/server/lib.rs
let statements = split_statements(query)?;
for sql in &statements {
    let mut stmt = conn.prepare(sql)?;
    // classify, execute, encode
}

2. The session builds a core statement. prepare_statement checks frontend-only cases, calls pg_query, translates the result, applies search_path, runs any prerequisite statements, and asks core to prepare the translated command.

PostgreSQL SQL
  → pg_query::ParseResult
  → PostgreSQLTranslator
  → turso_parser::ast::Cmd
  → turso_core::Statement

The key distinction: translate_with_prereqs adapts syntax trees. It does not execute SQL. The core boundary is prepare_translated_cmd_with_options.

3. The server turns core output back into PostgreSQL output. Because SELECT 42 has a result column, build_field_info chooses its PostgreSQL type and execute_query runs the statement and encodes each value.

T RowDescription · INT4 D DataRow · 42 C CommandComplete · SELECT 1 Z ReadyForQuery

The protocol meaning and byte layouts come from PostgreSQL's RowDescription, DataRow, and ReadyForQuery definitions.

Contributor Rule

Classify the broken artifact before choosing a file:

bytes → SQL string → PG AST → Turso AST → core Statement → Turso row → PG response

The boundary where the artifact first becomes wrong is usually where the fix belongs. For example, a correct value with the wrong PostgreSQL OID points to postgres/server, not the translator or VDBE.

Retrieval Check

SELECT 42 returns the value 42, but the client sees the column type as TEXT instead of INT4. Where do you inspect first?

Make It Real

Open these three call sites in order and explain aloud what artifact each returns:

  1. SimpleQueryHandler::do_query
  2. prepare_statement
  3. execute_query

Then close the lesson and reconstruct the five-stage pipeline from memory. That retrieval, not rereading, is what starts building durable recall.
